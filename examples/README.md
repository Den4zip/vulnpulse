# Примеры локального импорта

Все команды находятся в меню **Данные**. Сначала соберите приложение: `npm run build`, затем запустите его через `npm run dev`.

| Файл | Команда меню | Результат первого импорта в пустой профиль |
| --- | --- | --- |
| [fstec-demo.xml](fstec-demo.xml) | Импорт ФСТЭК из XML… | 2 записи источника и 2 BDU-карточки |
| [osv-demo.json](osv-demo.json) | Импорт OSV из JSON… | 3 записи источника и 3 OSV-карточки |
| [local-stack.example.json](local-stack.example.json) | Загрузить локальную конфигурацию ПО… | 4 компонента инвентаря, отдельный формат |

XML и OSV JSON — **синтетические тестовые данные**, не выгрузка актуальных уязвимостей и не официальные идентификаторы. Заголовки помечены «ДЕМОНСТРАЦИЯ». `BDU:0000-*` и `DEMO-LOCAL-*` используются только как учебные значения. Примеры не содержат реальных CVE aliases и не меняют реальные CVE-карточки по таким связям. Для проверки удобно использовать отдельный профиль: импорт сохраняет демонстрационные карточки в локальной БД.

Повторная загрузка тех же файлов не создаёт дублей. Число «Обработано записей» — размер входа, а не количество новых строк. XML и JSON загружайте соответствующей командой; файл стека не является OSV advisory. Все эти файловые импорты локальны, без передачи стека или querybatch. Загрузка зеркала ФСТЭК — отдельная сетевая команда.

## XML БДУ ФСТЭК

UTF-8, корень `vulnerabilities`, записи `vul`; `identifier`, `name`, `description`, даты `dd.mm.yyyy`. В примере показаны `vulnerable_software` и CDATA. Используется формат, который поддерживает текущий парсер приложения; это не подтверждение официальной XSD. Ручной импорт также принимает XML.GZ. Подробности и лимиты: [ФСТЭК](../docs/fstec-import.md).

## OSV JSON

Один advisory-объект или массив таких объектов. Пример — массив из трёх записей: npm SEMVER `[1.0.0, 1.2.0)`, PyPI с точной версией `2.0.0`, Maven с точной версией `3.0.0`. Пакеты тоже демонстрационные; они не совпадают с прежним примером инвентаря `local-stack.example.json`. `package.purl` в advisory не содержит версии; версии заданы в `versions`/`ranges`. Каждая запись имеет уникальный `id`, `modified` в UTC; `summary`, `details`, `published` и `affected` содержат описание и условия.

JSON читается как UTF-8 (BOM допустим), максимум 32 МиБ и 1000 записей. Неправильный JSON/metadata отклоняет весь импорт. Более старая или равная `modified` не заменяет сохранённую ревизию. Не все варианты условий OSV поддержаны matcher: неподдержанные правила дают `unknown`. Это формат локального импорта приложения; `DEMO-LOCAL-*` не предназначены для публикации в OSV.dev. Общие настройки/API-ключи здесь не хранятся.

Полноценная таблица уязвимостей и автоматический запуск matcher из приложения пока не подключены. Успех импорта отображается системным окном с количеством обработанных записей.

## Проверки

`npm run typecheck`, `npm test -- --coverage`, `npm run build`, `npm run e2e`. Unit-тесты импортируют именно эти файлы и проверяют повтор/отсутствие HTTP; для OSV проверяются локальные совпадения и исключение исправленной npm-версии. Electron E2E запускает собранное приложение в отдельном временном профиле и проверяет оба обработчика меню, worker, сохранённые записи/связи, повторы, ошибочный формат, отмену выбора и перезапуск. Только системные диалоги в E2E подменяются; сам Windows file picker не проверяется.
