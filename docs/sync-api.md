Контракт — `src/shared/api.ts`, сервисы — `src/main/services/{sync,imports,scheduler}.ts`, четыре обработчика — `src/main/ipc/sync.ts`. Последующее продолжение в этот же день подключило импорт/status/отмену к [React-каталогу](catalog-ui.md); Settings-экран ещё не подключён.

## Публичные методы

Все методы возвращают `Promise<ApiResult<T>>`. Общий guard проверяет управляемое окно, главный frame, origin и точный URL документа до обращения к сервису. В Main проверяются типы, разрешённые значения и отсутствие лишних полей; несколько IPC-аргументов отклоняются.

| Метод `window.electronAPI.sync` | Вход | Успешный ответ |
| --- | --- | --- |
| `status()` | Без параметров | `SyncView`: три сетевых источника, текущая операция, последние сетевой запуск и импорт, занятость Settings |
| `start({ feed })` | `cisa`, `nvd` или `fstec` | `OperationInfo` сразу после получения блокировки, без ожидания загрузки |
| `importFile({ kind })` | `osv`, `fstec` или `stack` | `OperationInfo` в фазе `selecting`; диалог открывается асинхронно в Main |
| `cancel({ operationId })` | UUID из текущей операции | Снимок той же операции с `cancelRequested: true` |

`start` использует прежний scheduler: CISA KEV, NVD (первый запуск — весь каталог), ФСТЭК **из неофициального зеркала GitHub**. Ручной запуск разрешён при выключенном автообновлении. Включение расписаний и интервалы меняются через Settings API. OSV остаётся только локальным JSON; произвольный URL, путь, raw JSON и SQL через эти команды не принимаются.

`importFile` выбирает один файл: OSV JSON, ФСТЭК XML/XML.GZ либо отдельный формат JSON-инвентаря стека. Настоящие readers, лимиты, XML worker/staging и атомарность импортов сохранены. Для IPC не показывается дополнительный диалог результата: будущий UI читает `status()`. Меню продолжает показывать итог и использует тот же ImportService.

## Операция и состояние

`OperationInfo` содержит UUID, `kind: sync|import`, `target`, `phase`, UTC `startedAt`, nullable `finishedAt`, `cancelRequested` и nullable `result`. Фазы: `selecting`, `running`, `completed`, `cancelled`, `failed`.

После успеха sync/OSV/ФСТЭК результат содержит только `processed`, `warnings`, `unchanged`; инвентарь — `added`, `skipped`, `total`. Число обработанных записей не равно числу новых уязвимостей. `unchanged: true` означает успешный условный HTTP-ответ 304, а не доказательство полноты базы. Ошибка операции видна как `failed`; пути, сообщения исключений, Axios config, raw payload и ключ NVD не возвращаются. Сообщения ошибок импорта в нативном меню также заменены постоянными безопасными строками.

`SyncView.active` — текущая операция либо null. `lastSync` и `lastImport` — последние операции соответствующего типа **в памяти этой сессии**, включая активную; это два ограниченных снимка, а не журнал. Запуски через меню и cron получают тот же UUID/учёт в scheduler и видны в status. После restart оба снимка null; никаких новых миграций или таблиц истории этим пунктом не добавлено.

`feeds` содержит три сетевых источника и прежние durable отметки `feeds.last_*`: enabled/running, время начала/конца последней попытки и `failed|cancelled|interrupted|null`. Конец попытки не означает время последнего успешного обновления. Произвольные старые ошибки сводятся к `failed`, даты ограничены и нормализованы либо null. Эти отметки не описывают локальные OSV/XML-импорты. Для них доступен сессионный `lastImport`; постоянная история импортов остаётся будущей задачей.

Пока нет IPC-событий и числового прогресса страниц/байтов: UI может опрашивать `status()` с разумным интервалом и прекращать polling после terminal-фазы/размонтирования. `osvMode: local-json` и `matchingRecomputed: false` явно отражают границы текущего поведения: импорт/синхронизация не запускают matcher и не сохраняют assessments.

## Блокировки, отмена и выход

Блокировка импорта действует от открытия селектора до окончания чтения/worker/транзакции. Общие guard-функции исключают наложение sync, импорта и записи Settings/ключа. Стек также запрещает свои записи во время импорта. При занятости команда возвращает `BUSY`, без очереди. Чтения остаются доступны. Внутри Main сохраняется синхронный SQLite commit; мгновенная отмена CPU/SQL-работы не гарантируется.

Отмена требует ID именно активной операции. Неактуальный или уже завершённый ID даёт `CONFLICT` и не отменяет следующий запуск. `cancelRequested` означает запрос отмены, а не завершившийся откат. Применённый commit остаётся `completed`; при NVD ранее применённые страницы сохраняются, незавершённое окно возобновляется прежним механизмом checkpoint.

Согласно [Electron dialog API](https://www.electronjs.org/docs/latest/api/dialog#dialogshowopendialogwindow-options), `showOpenDialog` возвращает Promise с `canceled`/`filePaths` и принимает родительское окно; у него нет AbortSignal-параметра. Сверены официальная документация и установленные типы Electron 45. IPC-селектор привязан к управляемому окну, после закрытия/замены окна его выбор игнорируется. Отмена во время селектора запрещает последующий импорт, но **не закрывает нативный диалог программно**: его нужно закрыть вручную. До этого сохраняется блокировка; штатный выход ждёт его завершения. Физическое открытие/закрытие системного диалога проверкой с подменой не подтверждено.

При выходе снимаются обработчики и подписки, команды больше не принимаются, scheduler/import получают отмену, их задачи и незавершённая запись Settings завершаются до закрытия SQLite. Секрет NVD по-прежнему читает только Main перед сетевым запуском.
