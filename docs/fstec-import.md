# Импорт БДУ ФСТЭК

Реализованы ручной XML/XML.GZ и сетевой импорт из публичного неофициального зеркала. Доступны в меню **Данные**:

- **Импорт ФСТЭК из XML…** — системный выбор локального файла.
- **Загрузить ФСТЭК из зеркала…** — запрос общего снимка, без передачи стека.
- **Отменить текущий импорт** — отмена загрузки/worker. При выходе приложение отменяет активную операцию, ждёт завершения worker и закрывает БД.

Это команды Main, без SQL или XML-парсера в Renderer. Таблица уязвимостей и полноценный IPC ещё не реализованы. После импорта показываются число обработанных записей и число предупреждений; одинаковые/устаревшие записи входят в обработанное количество.

Для проверки доступен [fstec-demo.xml](../examples/fstec-demo.xml): две синтетические записи, не официальный экспорт и не реальные уязвимости. [Инструкция и пример локального OSV JSON](../examples/README.md).

## Источник и формат

Официальная [страница БДУ](https://bdu.fstec.ru/vul) при проверке 2026-11-06 вернула TLS-ошибку; проверка сертификатов не отключалась. Официальный API не реализован. Базовый сетевой путь выбран по разрешению пользователя — [неофициальное зеркало velvetway/bdu-fstec-mirror](https://github.com/velvetway/bdu-fstec-mirror), файл [vulxml.xml.gz](https://raw.githubusercontent.com/velvetway/bdu-fstec-mirror/main/data/vulxml.xml.gz). Актуальность и достоверность зависят от этого зеркала; это не подтверждение свежести официальной базы.

Структура сверена по фрагменту настоящего снимка и [коду чтения зеркала](https://github.com/velvetway/bdu-fstec-mirror/blob/332170b68737488b32177f2c75360e7f6bc8e3da/scripts/build_db.py): корень `vulnerabilities`, записи `vul`, поля `identifier`/`name`/`description`, `publication_date`/`last_upd_date`, `identifiers/identifier` с атрибутом `type="CVE"`, `vulnerable_software/soft`, `cvss`/`cvss3`. Это наблюдаемый формат `fstec-xml-v1`, не официальная XSD и не гарантия совместимости со всеми будущими экспортами. Первоначально фрагмент изучен из закреплённого коммита `0c190b9fa21d9b89cc9a6834652fcaa8ffc17f46`.

Поддерживается UTF-8, BOM, XML 1.0, комментарии и CDATA. ZIP и XLSX не принимаются: ZIP официальной выгрузки нужно предварительно распаковать. `.gz` распаковывается в worker. Иные кодировки/неизвестная структура отклоняются.

## Обработка и сохранность

HTTP проходит только через `HttpClient`; endpoint фиксирован, произвольные URL не принимаются. Условный запрос использует `If-None-Match`; 304 принимается только при ранее применённом ETag. Данные и новый ETag применяются одной транзакцией. Успешный ручной импорт сбрасывает ETag зеркала. Автоматического расписания пока нет.

Worker читает поток, распаковывает gzip и выделяет отдельные `vul`, учитывая комментарии, CDATA и кавычки в тегах. Каждую запись валидирует и разбирает `fast-xml-parser@5.12.0`; типы/даты/ссылки нормализуются там же. DTD и объявления сущностей запрещены. В Main не разбирается XML.

Проверенные записи складываются во временный NDJSON-файл. Main после успешного завершения worker проверяет протокол, размер, количество и SHA-256 staging-файла, читает его ограниченными порциями и применяет весь импорт в одной SQLite-транзакции. Ошибка структуры, отмена до применения или ошибка БД сохраняет прежнее содержимое и ETag. После операции worker завершается, временный каталог удаляется с повторами; при ошибке удаления выдаётся сообщение в журнал без payload, уже выполненный импорт не объявляется откатившимся.

XML разбирается без накопления всего документа/набора записей в памяти. Финальное применение SQLite остаётся синхронным в Main: на большом снимке интерфейс может временно не отвечать, а кнопка отмены в этой фазе не обрабатывается до окончания транзакции. Перенос БД в worker этим изменением не выполнялся. При аварийном завершении процесса возможен оставшийся временный каталог.

В `source_records` хранятся BDU ID, исходная XML-запись, все разобранные поля, происхождение `manual`/`mirror` и предупреждения. Явные корректные CVE создают связи с каноническими карточками; без них используется BDU ID. Некорректная ссылка типа CVE сохраняется в raw с предупреждением и не создаёт выдуманной связи. Название/текст версии ПО не превращаются в CPE/PURL или безусловное совпадение. CVSS и признаки эксплуатации сохраняются в raw, не перезаписывая технические поля NVD/CISA.

Существующие статусы, заметки, KEV и другие источники сохраняются. Новая ревизия меняет только свою исходную запись/связи; старые карточки с workflow не удаляются. Свежесть — по `last_upd_date`, при его отсутствии/некорректности используется корректная `publication_date`. Неверные даты сохраняются в raw с предупреждением. Если обе даты неизвестны, обновление уже сохранённой недатированной записи пропускается. Равная дата дня и более старая дата не заменяют применённую ревизию: изменения внутри одного дня автоматически не разрешаются. Исчезновение записи из снимка не означает удаление или Patched.

## Лимиты

- До 64 МиБ сжатого ответа/файла, до 1 ГиБ распакованного XML.
- До 150 000 записей; одна XML-запись до 2 МиБ, глубина до 32.
- До 100 корректных CVE-ссылок на запись; дубликаты BDU ID отклоняются.
- Staging до 1,5 ГиБ; heap worker до 256 МиБ.
- Worker — 5 минут по умолчанию; внутренний timeout настраивается в пределах 1–600 000 мс.
- `parse()` буферизует не более 5000 записей; полные снимки идут через `importFile()` / `syncMirror()` с дисковым staging.

## Проверки 2026-11-06

- `npm run typecheck`, `npm run build`, `npm test -- --coverage --coverage.reporter=text --coverage.reporter=json-summary` прошли: **486/486 тестов**, 19 файлов. Весь matcher сохранил 100% четырёх метрик.
- Тесты используют настоящий worker, выданный electron-vite через `?modulePath`, и настоящую SQLite. Проверены XML/GZ, UTF-8/CDATA, границы токенов, отмена/timeout/падение worker, ошибки БД, ETag/304, повторы, даты и сохранность workflow. Сетевые ошибки проверены через подмену внешнего Axios transport.
- Реальный полный снимок импортирован через штатный `syncMirror()` в отдельную in-memory БД: **86 664 записи источника**, **79 346 канонических карточек**, **116 978 связей**, **87 предупреждений**, **158 336 мс** вместе с сетью/разбором/записью. Это один наблюдавшийся запуск, не нагрузочный SLA. Тестовая загрузка не передавала стек и не использовала рабочую БД.
- Отдельно сохранён исследовательский публичный gzip-файл вне репозитория в `.runtime`: 29 115 230 байт, XML по gzip-трейлеру 565 033 339 байт, SHA-256 `8dfeb048ab8e33611e0f985a7a7c07bc791051ca186f84b4e2b2127ffffe2fc6`. Это контрольная сумма исследовательской копии, не подпись ФСТЭК и не доказательство тождества меняющегося `main` во все моменты проверки.
- Первая проверка полного снимка выявила некорректные CVE, следующая — некорректные даты; добавлена их обработка с предупреждениями без выдуманных связей/дат. Лимит 512 МиБ оказался меньше действительного XML и поднят до 1 ГиБ. Неудачные попытки не применили данные в БД.
- В Electron проверено наличие меню и открытие системного выбора файла в отдельном профиле. Дальнейшее управление интерфейсом пользователь остановил физическим Escape; успешный импорт через сам GUI не заявляется. Сам ручной путь подтверждён интеграционными тестами.
- Общая Vitest-метрика services: 83,54% statements / 83,15% branches / 92,38% functions / 87,04% lines. Код отдельного собранного worker выполняется вне instrumented-процесса Vitest и отражён нулём в отчёте исходников; это ограничение измерения, а не отсутствие реальных worker-тестов. Покрытие не исключалось ради процента.

Новая зависимость закреплена ровно `5.12.0`; установка без install-скриптов сообщила 0 уязвимостей. Context7 и установленные типы использованы для XML API; механизм `?modulePath` сверён с [документацией electron-vite](https://electron-vite.org/guide/dev). Установщик/ASAR, Playwright E2E, восстановление после аварийного завершения большого импорта и производительность UI при SQLite commit ещё не проверены.
